## mental model - two locations, one explicit sync step

Power BI Desktop is Windows-only and cannot open this repo's WSL working tree directly (unlike Jupyter's bind mount - there is no live-mount equivalent here). The git-tracked copy lives at `$POWERBI_REPO_DIR` (`powerbi/reconciliation-dashboard-template/`); the copy Power BI Desktop actually opens lives at `$POWERBI_WINDOWS_DIR` (see `.env`, both machine-agnostic/machine-specific respectively). Nothing round-trips automatically - every change in either direction needs an explicit:

```bash
./scripts/05-powerbi-sync.sh push    # repo -> windows, before opening in Desktop
./scripts/05-powerbi-sync.sh pull    # windows -> repo, after saving in Desktop
./scripts/05-powerbi-sync.sh verify  # read-only, confirms both sides still match
```

Full design rationale: `docs/features/06-powerbi-dashboard-setup.md`. Short user-facing version: `powerbi/README.md`.

## the safe-edit boundary - read this before hand-editing anything

Two costly real failures (`06.IS.02`: Desktop refused to open a hand-generated `.Report`; `06.IS.04`: Desktop crashed saving one) settled this, don't relitigate it per-edit:

| id | content                              | hand-editing it directly | 
| -- | ---------------------------------------- | ---------------------------| 
| 01 | `.SemanticModel` TMDL (tables, columns, measures, M-queries) | **safe** [01]  | 
| 02 | a new object added to an *existing, already-valid* `.Report` page | **safe** [02]  | 
| 03 | a whole new `.pbip`/`.Report`/`.SemanticModel` generated from scratch | **not safe** [03] | 
| 04 | `relationships.tmdl`, new pages, bindings against not-yet-loaded columns | **not safe** [04] | 

01. documented, externally-editable format - proven repeatedly this session (a measure, three postgres-backed tables).
02. e.g. one more visual, modeled on a sibling already in the project - extends proven content, doesn't fabricate a schema from nothing.
03. `report.json`/PBIR is explicitly undocumented-for-external-editing during preview - two different real Desktop crashes came from this (`06.IS.02`, `06.IS.04`).
04. no proven-working reference to model against in this project yet - a human GUI action, not an agent task.

If a new `.pbip` needs to exist at all: it does not get generated by a script. `scripts/utils/powerbi-sync.py`'s `cmd_scaffold` verifies-and-instructs only - a human creates Report + SemanticModel **together** in one Desktop session (File > New > blank report > Get Data > Save As `.pbip`), because that pairing is what keeps them internally consistent; `pull` then captures it. Never resurrect a from-scratch generator for this.

**Before writing any TMDL/PBIR syntax you're not certain of**, verify it against real ground truth first, in this order:

1. An existing file already in this project doing something similar - `powerbi/reconciliation-dashboard-template/**/*.tmdl` for TMDL shape, the `.Report/definition/` tree for PBIR shape. This is how the postgres tables, the second visual, and every TMDL fix this session were actually built - never invent a property name from memory when a real sibling object is one `Read` away.
2. Official docs, when no sibling exists: [TMDL Column reference](https://learn.microsoft.com/en-us/analysis-services/tmdl/tmdl-reference-tabular-object) for column/table properties, [PostgreSQL.Database M reference](https://learn.microsoft.com/en-us/powerquery-m/postgresql-database) for connector syntax, [PBIP report folder reference](https://learn.microsoft.com/en-us/power-bi/developer/projects/projects-report) for what's/isn't externally-editable. This caught a real mistake before it shipped: `dataType: datetimezone` isn't a valid TOM column type (TOM has no timezone-aware column type at all) - `dateTime` is, confirmed against the reference above before pushing, not after a Desktop failure.

Never fall back to "it's probably fine" on either point - that assumption is exactly what caused `06.IS.02`/`06.IS.04`.

## editing TMDL directly

All TMDL and PBIR files under `powerbi/` use **CRLF line endings** (Power BI Desktop's own convention, confirmed by inspecting real Desktop output) and **no BOM**. Match it or every future Desktop save will show a spurious whole-file diff:

```python
# preserves existing CRLF when editing in place
with open(path, "r", newline="") as f:
    content = f.read()
content = content.replace(old, new)
with open(path, "w", newline="") as f:
    f.write(content)

# writing a brand-new file with the same convention
with open(path, "w", newline="\r\n") as f:
    f.write("\n".join(lines) + "\n")
```

**Never write a database credential into a TMDL M-query or any other git-tracked file.** Power BI Desktop's Postgres connector (`PostgreSQL.Database("host:port", "database", [Query="..."])`) takes only server/database/SQL in the M query itself - username/password are entered once, interactively, in Desktop's own encrypted credential prompt, and live only in `.pbi/` (already gitignored) or Desktop's local credential store.

## pushing an edit and resolving a conflict

```bash
./scripts/05-powerbi-sync.sh push
```

`push`/`pull` compare each side's current checksums against `.sync-manifest.json` (the last-known-both-sides-agreed state) - a file only moves if it actually changed, and if **both** sides diverged from the manifest independently, the command refuses rather than picking a winner:

```
[FAIL] push: /mnt/... has un-pulled changes, would overwrite: [...]
[FAIL] pull: both sides changed since last sync - resolve manually
```

If the listed files on each side genuinely don't overlap (e.g. you edited a TMDL table while a prior Desktop session touched a different `visual.json`), this is a real, resolvable non-overlapping conflict, not a bug - resolve it by hand:

1. Copy whichever windows-side file(s) are listed into the repo copy (`cp` - these are Desktop's own edits, capture them as-is).
2. **Rebuild the manifest from the windows side's checksums specifically** - not the repo side's. The manifest must represent the last point both sides *actually agreed*; rebuilding from the repo's own just-edited state makes every windows-side file that hasn't received those edits yet look "diverged" and `push` will refuse again for the wrong reason.
   ```python
   import importlib.util
   spec = importlib.util.spec_from_file_location("powerbi_sync", "scripts/utils/powerbi-sync.py")
   m = importlib.util.module_from_spec(spec); spec.loader.exec_module(m)
   from pathlib import Path
   import os
   repo_dir, windows_dir = Path(os.environ["POWERBI_REPO_DIR"]), Path(os.environ["POWERBI_WINDOWS_DIR"])
   m.save_manifest(repo_dir, m.checksums(windows_dir), "manual-merge")
   ```
3. `push` again - it now sees the windows side matching the manifest and copies only your genuinely-new/changed repo-side files.

Confirm independently, never trust the script's own summary alone:

```bash
set -a && source .env && set +a
diff -rq "$POWERBI_REPO_DIR" "$POWERBI_WINDOWS_DIR" --exclude '.pbi' --exclude '*.abf' --exclude '.sync-manifest.json'
```
(`.pbix` also excludes cleanly - it's synced out of scope by design, not a tracked deliverable.) A lone `Only in .../windows: *.pbix` line is expected and fine.

## getting it ready for the user to open

After a clean `push` + `verify` + independent `diff -rq`, the template is ready at `$POWERBI_WINDOWS_DIR` - tell the user to open the `.pbip` from there in Power BI Desktop. Set expectations rather than letting them re-diagnose known, already-documented behavior:

- **First open of any project with no local `.pbi/cache.abf`** (a fresh pull, or first open ever) may show "some of the tables have incomplete or no data" - expected per Microsoft's own docs (the model definition loads, data doesn't until a refresh), not a bug. **Home > Refresh** fixes it.
- **A live postgres connection** prompts for credentials once (Database auth) and, since this repo's docker postgres has no SSL configured, an unencrypted-connection warning to click through - both normal for this setup, not errors.
- **No repair prompt at any point** is the actual pass signal that whatever was just edited is valid Power BI content, not merely well-formed text - if one appears, stop and diagnose (see below) rather than asking the user to click through it.

## when something unexpected happens

Log it under `docs/features/06-powerbi-dashboard-setup.md` -> Validate -> Issues as the next `06.IS.<n>`, following the `feature-implementation-guide` skill's protocol (problem description / exception / triggering actions / hypothesis / diagnostic steps / diagnostic details). Diagnose the same way the safe-edit boundary above was established - diff against a real, already-proven-working sibling object or file in this same project first, official docs second, never a second guess from memory. `06.IS.02` and `06.IS.04` are worked examples of exactly this process, including the pivot each one forced (a course change gets recorded as a `## Revisions` entry in the tracker, not silently folded into the next attempt).
